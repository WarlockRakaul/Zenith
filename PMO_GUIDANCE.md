# Zenith PMO workstream guidance

Status: proposed for integration, 2026-10-12. Joe approved the prevention review on 2026-10-11 and requested submission and distribution to all project PMO guidance. This document supplies the bounded repository-safety guidance for Zenith when integrated into main. It adopts only [Git-Aware Workstreams at the reviewed Studio commit](https://github.com/WarlockRakaul/studio-os/blob/81397e848ffe6d36a32c3c3e9b56cbe4f79b8674/MODULES.md#module-03-git-aware-workstreams), reproduced below for local reading. It does not adopt all Studio Core, other modules, creative governance, or an automatic update mechanism. The exact source remains fixed until a separately authorized change.

Projects using Git may opt into branch-aware and concurrent-workstream safeguards. Actual Git state remains authoritative for branches, commits, worktrees, and repository history; durable project state records the purpose, approved boundaries, unresolved issues, and next authorized action of each relevant workstream. Agents must inspect and reconcile actual Git state before editing rather than relying on stale branch metadata. The module should scale from a single active workstream to multiple concurrent branches without requiring artificial complexity. Destructive or cross-workstream integration operations require explicit authorization or a previously approved plan.

Useful when branch or worktree confusion could put approved work at risk. Local input: actual repository locations, relevant workstream purpose and boundaries, and expected branch/checkpoint only where useful. One workstream does not require a concurrency system.

Before editing, inspect actual repository root, branch, HEAD, working tree, and relevant worktree/base/divergence information; compare that observation with the selected workstream purpose. Investigate mismatches without silently switching branches or rewriting recorded purpose to match. Do not duplicate full Git history or invent a global active-branch value. Record meaningful context changes through normal closeout under [CORE-07](https://github.com/WarlockRakaul/studio-os/blob/81397e848ffe6d36a32c3c3e9b56cbe4f79b8674/CORE.md#core-07-durable-operational-handoff); the fact ownership boundary is [CORE-08](https://github.com/WarlockRakaul/studio-os/blob/81397e848ffe6d36a32c3c3e9b56cbe4f79b8674/CORE.md#core-08-single-authority-per-rule-or-fact). This module does not authorize integration merely because branches share ancestry.

Concurrent editing workstreams must use separate working folders, normally Git worktrees with distinct branches or detached HEADs. Separate chats or branch names do not isolate a shared checkout. Reuse a suitable existing worktree when available; otherwise create one from the intended workstream checkpoint, within existing authorization. Do not silently start from whichever branch another chat left active. A shared folder may be used sequentially after unfinished work is preserved and the intended checkout is verified. Do not switch branches underneath another active session or bypass Git's protection against checking out the same branch in multiple worktrees.

Before editing, use available session information to check whether another editing session uses the same working folder. Git state alone cannot establish session ownership or absence of concurrent writers; if session visibility is unavailable, do not claim that exclusivity was verified. When shared use is known or reasonably suspected, arrange a separate checkout for this workstream or establish sequential use before writing. Agents are responsible for arranging isolation within existing authorization and reporting the resulting folder and checkpoint, rather than routinely assigning worktree setup to the human. Seek clarification when the intended starting checkpoint, ownership of unfinished files, or authority for a necessary move is unresolved; do not request repeated approval for already-authorized setup.

Repeat the state check when resuming work, after a handoff, and before committing or integrating. If the checkout changed unexpectedly, stop affected writes, identify the workstream owning the changes, and reconcile without staging, stashing, moving, or discarding another workstream's files. Preserve relevant tracked, untracked, and required ignored local files before an authorized move or branch switch; a commit does not preserve files it excludes. The normal handoff should identify the working folder, intended workstream/checkpoint, unfinished-file locations, and next action only where needed to resume safely.

Diagnose filesystem and sandbox access failures separately from Git branch conflicts. Verify that the selected workspace grants access to the actual repository root and required Git metadata, especially when the application project is a subdirectory. Report the failing path and command, distinguish an approved elevated diagnostic from normal sandbox access, and verify normal access after any authorized environment repair. Branch switches, merges, or commits are not access repairs. Keep existing sandbox protections; use supported workspace configuration or authorized environment repair rather than broadly weakening permissions. See the non-governing [worktree and access guide](https://github.com/WarlockRakaul/studio-os/blob/81397e848ffe6d36a32c3c3e9b56cbe4f79b8674/GIT_WORKSTREAMS.md) for a practical procedure.
